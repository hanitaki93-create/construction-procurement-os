# 5. Core evidence identity model

## EvidenceRecord

Durable business-evidence identity/lineage within tenant scope.

It does not imply current validity, acceptance or authority.

## EvidenceVersion

Immutable identity for one exact captured/source/issued version.

New load-bearing source revision/content state creates a new EvidenceVersion.

Historical versions remain identifiable while retained.

## ContentIdentity / IntegrityAssertion

Technical content/integrity identity is separate from EvidenceRecord/EvidenceVersion business identity.

Same bytes/hash do not prove same source principal, business submission, revision lineage or effect.

Hash/integrity does not prove content truth or business authority.

## CaptureObservation

One EvidenceVersion may have multiple capture/channel occurrences.

Repeated channel capture does not create duplicate source version where equivalence is proven.

## EvidenceBinding

Typed relation from exact evidence/source location to domain fact/event/decision or evidence action.

Bounded roles include SOURCE_BASIS, ISSUED_OUTPUT, SUPPORTING_EVIDENCE, VALIDATION_EVIDENCE, CORRECTION_EVIDENCE, TRANSMISSION_EVIDENCE and ANCILLARY_REFERENCE.

No arbitrary knowledge graph.

# 6. Historical RelianceBinding — remediated blocker

Once an effective load-bearing domain fact/event/decision relies on evidence, preserve immutable historical **RelianceBinding** semantics:

- exact domain event/decision;
- exact EvidenceVersion;
- exact SourceLocator where applicable;
- binding role;
- source principal/context;
- governing policy/config/authority version where material;
- relied-on time/context;
- action/audit provenance.

Later evidence revision cannot update this binding.

If Quote Rev0 caused AwardDecision and Rev1 arrives later, AwardDecision remains bound to Rev0. Re-evaluation/correction creates new domain event + new bindings.

Mistaken binding correction is history-preserving: original binding, reason, corrected binding, authority/time and affected-domain disposition remain explicit.

Ancillary links may evolve but are distinguishable from effective RelianceBinding.

PRODUCT_ISSUED output similarly binds immutably to the issue/domain action that produced it.

# 10. ReconstructionAnchorTest — remediated blocker

External reference can be load-bearing SOURCE_BASIS only when source semantics identify the exact immutable/historically addressable version and prevent later current-state substitution.

Required semantic properties as applicable:

1. authoritative external source/system;
2. object identity;
3. exact immutable/historically addressable version/revision identity;
4. source semantics showing version is not an alias to current content;
5. source principal/authority;
6. source locator;
7. effective/source context;
8. observed/fetched/freshness/conflict context;
9. retrieval/reference path sufficient for supported reconstruction while valid retention/source-access basis exists.

A stable object ID that always returns current content FAILS.

A mutable URL/path/current token FAILS unless source semantics actually pass the exact-version test.

If external source cannot pass, immutable local capture is required where permitted for a load-bearing exact-reconstruction dependency.

If neither path exists, the dependency remains unresolved and cannot satisfy the evidence guard.

Later legitimate source loss/disposition changes availability/reconstruction limitation; it does not rewrite original valid reliance.

# 11. Integrity / hashing

IntegrityAssertion identifies exact EvidenceVersion/representation, method, algorithm/scheme/version where applicable, digest/reference, validation/calc context and revalidation history.

Hash exact representation as such.

OCR, normalized PDF, rendering, translation and extracted data have separate identities/integrity assertions and explicit derivation relations.

No hidden canonicalization.

- same EvidenceVersion can receive new integrity assertion when algorithms evolve;
- old assertion history remains;
- unavailable original payload cannot receive a fabricated “stronger original hash” by hashing a derivative.

Hash surviving payload disposal still needs retention basis and cannot recreate disposed content.

# 17. Communication-conditioned effectiveness — remediated blocker

P1.6 supports exactly two semantic patterns.

## Pattern A — EFFECTIVE_THEN_NOTIFY

Owning domain event becomes effective under its own guards first.

Exact artifact is then issued/communicated.

Notification failure does not silently reverse the effective event.

Separate domain correction/withdrawal is required if needed.

## Pattern B — COMMUNICATION_GATED_EFFECTIVENESS

Where issue/dispatch/delivery/ack/content response is a condition of effectiveness:

1. owning domain creates/authorizes a pre-effective immutable business basis with enough final content/identity/number/authority to generate outgoing artifact;
2. P1.6 freezes exact EvidenceVersion/Transmittal;
3. required communication observation occurs;
4. owning-domain effectiveness command consumes exact communication evidence + pre-effective basis + current authority/invariants;
5. domain event becomes effective with causal binding;
6. effective time may derive from named observation if governing rule requires.

Crash after dispatch before effectiveness command is safe: immutable dispatch observation exists; idempotent domain command can retry without reissue.

If rule requires delivery, send cannot substitute.

If rule requires substantive acceptance, receipt acknowledgment is insufficient.

No hidden third pattern.

Domain profile declares Pattern A/B and the qualifying observation for Pattern B.
