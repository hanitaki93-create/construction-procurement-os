# 3. Immediate sequence

## P2.1 — Physical architecture decision frame

Decide and hostile-audit:

- modular-monolith versus service boundaries;
- transactional database/event/outbox strategy;
- object/evidence storage and immutable identity;
- queue/worker/search/cache boundaries;
- tenant isolation and authorization enforcement;
- API/operation execution pattern;
- frontend application/surface strategy;
- observability/security/deployment baseline;
- AI provider-neutral seam without AI dependency.

Every choice must prove preservation of the frozen semantics.

## P2.2 — Build-block dependency graph

Compile approximately **12–18 major build blocks**, likely including:

1. repository/tooling/quality foundation;
2. tenant, project, identity and authority context;
3. operation registry, command execution, idempotency and audit;
4. evidence/file/version/issue foundation;
5. requirement allocation and optional package;
6. RFQ/tender lifecycle and external task grants;
7. supplier submissions, revisions and buyer capture;
8. normalization, comparison and field/schema registry;
9. recommendation, approval, AwardDecision and handoff;
10. deterministic reporting/control pack;
11. interaction shell, queues, disclosures and recovery;
12. integration/migration/provider-neutral email seams;
13. NFR/security/privacy/residency/deployment hardening;
14. optional P07 commercial core after feasibility authorization;
15. optional AI capability substrate after deterministic path/evaluation authorization;
16. validation, pilot and release instrumentation.

The exact count may change only through dependency and scope analysis, not convenience.

## P2.3 — First build prompt

Generate the first executable build prompt only after:

- physical architecture PASS;
- build-block graph PASS;
- exact block scope and dependencies;
- acceptance tests and rollback;
- V1/V2 authorization status is explicit.

# 4. Build-block contract

Every major block must contain:

- block identifier and objective;
- included/excluded requirements;
- frozen source references;
- dependency and unlock conditions;
- physical design decisions;
- schemas/interfaces/events at implementation level;
- operations and authority matrix;
- evidence/audit/recovery behavior;
- conventional UI/API/report ownership;
- NFR and security tests;
- golden-thread acceptance tests;
- migration/rollback strategy;
- hostile misuse and failure scenarios;
- exact completion gate;
- explicit non-goals and later blocks.

A block may be divided into smaller implementation prompts, but completion is judged at the major-block gate.

---

# 5. Efficiency rule

Phase 2 should be aggressive but not monolithic.

Preferred pattern:

- one integrated physical-architecture candidate;
- one hostile audit/remediation cycle;
- one dependency-ordered block map;
- then large but bounded build prompts.

Do not create hundreds of tiny prompts that lose architecture context.

Do not create one whole-product prompt that makes recovery, review and dependency control impossible.

Target: first executable build prompt after **one or two focused Phase 2 architecture/decomposition runs**, subject to no semantic contradiction and V1/V2 authorization.
